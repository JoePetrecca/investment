Ruff

09

Ruff keeps your Python code clean automatically. It formats your code, fixes small issues, enforces consistent naming like snake_case, and organizes imports.

Once this is set up, you really do not think about formatting anymore. You just write code and save.

Install Ruff

Go to Extensions in VS Code, search for Ruff, and install it.

Make it run automatically

You want Ruff to:

Run on save

Every saved Python file gets checked automatically.

Fix issues

Small formatting and linting problems can be cleaned up for you.

Organize imports

Imports are sorted and cleaned without manual work.

That is controlled by your settings.json. Do not overthink it. Just make sure:

  • Format on save is on
  • Ruff is your Python formatter
  • Fixes and import organization are enabled

The pyproject.toml

This file tells Ruff how to behave, like line length, naming style, and formatting rules.

Do not spend time trying to perfect this.

Instead:

  • Ask a generative AI to generate it for you
  • Tweak it slightly if needed
  • Move on
Give me a Ruff config toml with 100 character line length, snake_case, and auto-fixing.

Paste it in and you are done.

Notebooks

For notebooks, just ask an AI how to enable Ruff for notebooks in VS Code, or how to run it manually.

Typically, you will use:

VS Code command
Cmd/Ctrl + R, then U

And it will clean the notebook.

That is it

Do not over-engineer this. The goal is:

  • Save your file
  • Code gets cleaned automatically

Once that works, you are good.

Warning Don't have Ruff automatically change variable names for you, as that can have cascading effects. Instead, allow it to underline variable names that you consider not in the desired style, and then you, as the programmer, can choose to fix them.

Example pyproject.toml for Ruff

Here is a reasonable starter configuration of a pyproject.toml file:

pyproject.toml
[tool.ruff]
line-length = 100
target-version = "py311"
preview = true

[tool.ruff.lint]
select = [
"E",
"F",
"N",
"I",
"B",
"UP",
"SIM",
"C4",
"ARG",
"RUF",
]

ignore = [
"E501",
]

fixable = ["ALL"]
unfixable = []

[tool.ruff.lint.per-file-ignores]
"*.ipynb" = [
"E402",
]

[tool.ruff.format]
quote-style = "single"
indent-style = "space"
skip-magic-trailing-comma = true
docstring-code-format = true

What this does

line-length = 100 tells Ruff to format code around a 100-character line length.

target-version = "py311" tells Ruff to assume Python 3.11. This matters because Ruff can suggest newer Python syntax only when that syntax is valid for your Python version.

preview = true enables newer Ruff rules and formatting behavior that may not be fully stabilized yet.

The select section turns on groups of linting rules:

E Basic Python style errors
F Likely bugs, such as undefined variables or unused imports
N Naming conventions, such as snake_case variables and CamelCase classes
I Import sorting
B Bug-prone code patterns
UP Suggestions for newer Python syntax
SIM Simplifications for overly complicated code
C4 Cleaner list, set, and dictionary comprehensions
ARG Unused function arguments
RUF Ruff-specific best-practice rules

ignore = ["E501"] ignores line-length lint warnings because the formatter already handles line wrapping.

fixable = ["ALL"] allows Ruff to automatically fix anything it knows how to fix.

unfixable = [] means there are no selected rules that Ruff is forbidden from fixing.

The notebook-specific ignore:

Notebook ignore
"*.ipynb" = ["E402"]

Allows imports to appear outside the top of the file in Jupyter notebooks. This is useful because notebooks are cell-based, and it is common to have imports in different cells while exploring.

The formatting section says:

  • Use single quotes
  • Use spaces for indentation
  • Avoid magic trailing comma behavior
  • Format code examples inside docstrings
Warning If you are working inside an existing collaboration, use that collaboration's Ruff configuration. For example, TARDIS has its own config file, and that should be treated as the source of truth when contributing to TARDIS code.
Tip For personal projects, a local pyproject.toml like this is a good starting point. For shared projects, follow the project's existing config so everyone formats code the same way.
Tip A fully custom pyproject.toml can be intimidating to write and understand. As mentioned above, you can ask an LLM to help generate one. Give it the Ruff rules, or ask it to look them up, and have it ask you questions about your coding style, formatting preferences, and which kinds of linting rules you want to enforce.
